# Q4 Matter 표준 매핑 · SDK · 개발킷 · Multi-Admin 시연 가능성

조사일 2026-09-09. 도구: WebSearch 8회 · WebFetch 22회. 출처 태그 [S1]~[S8]은 아래 「출처」 표, 태그 없는 검증 문자열은 「확인 못 한 것 / 접근 불가」의 "보조 확인" 항목.

### 발견

**(a) 표준 디바이스 타입·클러스터**

1. Google Home 공식 지원 표에서 Occupancy Sensor 의 애플리케이션 클러스터는 Occupancy Sensing, Contact Sensor 는 Boolean State, On/Off Light 와 On/Off Plug-in Unit 은 On/Off + Level Control, Smoke Detector 는 Smoke CO Alarm(스펙 1.2)이다 — 원문: "Occupancy Sensing" / "Boolean State" / "Level Control" and "On/Off" / "Smoke CO Alarm" [S5]
2. Google Home 은 표에 없는 디바이스 타입을 공식 지원하지 않는다고 명시한다 — 원문: "Device types other than the ones listed here are not officially supported in the Google Home ecosystem." [S5]
3. Matter 1.5(2025-11-20 발표)에서 카메라 디바이스 타입이 표준에 들어갔고, 영상·음성 스트리밍은 WebRTC 를 쓴다 — 원문: "Matter 1.5 introduces one of the most anticipated additions to the specification: cameras." / "Matter cameras support live video and audio streaming using established WebRTC technology" [S1]
4. Matter 1.5 는 카메라 외에 closures(창 가리개·게이트·차고문)와 soil sensor 도 추가했다 — 원문: "Building on prior releases, 1.5 introduces a revamped and unified approach to closures, covering a broad range of devices such as window shades, drapes, awnings, gates, and garage doors." / "Matter 1.5 extends the standard's reach into new garden and plant-care use cases with support for soil sensors." [S1]
5. matter.js 의 생태계 검증 표는 On/Off Light 와 Contact Sensor 를 디바이스 타입 ID 와 함께 검증 대상으로 싣고 있다 — 원문: "On/Off Light (ID: 0x0100)" / "Contact Sensor (ID: 0x0015)" [S4]
6. Home Assistant Matter 통합이 노출하는 엔티티 종류에 Binary sensor·Switch·Light·Siren 등이 포함된다 — 원문: "Binary sensor, Button, Climate, Cover, Fan, Light, Lock, Number, Select, Sensor, Siren, Switch, Update, and Water heater" [S7]

**(b) Multi-Admin 정의와 복수 컨트롤러 시연 방법**

7. Google 공식 프라이머는 Fabric 을 같은 보안 도메인을 공유하는 노드 집합으로 정의하고, 한 노드가 둘 이상의 Fabric 에 커미셔닝될 수 있는 성질을 multi-admin 이라 부른다 — 원문: "Whenever a set of Devices in a network shares the same security domain, and thus allows secure communication between Nodes, this set is called a Fabric." / "Nodes may also be commissioned on more than one Fabric. This property is often referred to as multi-admin." [S2]
8. Silicon Labs 공식 문서는 Multi-Admin 을 한 기기가 여러 Matter 생태계에 동시에 참여하는 기능으로 정의한다 — 원문: "Matter devices can participate in multiple Matter ecosystems simultaneously through a feature called Multi-Admin." [S3]
9. 두 번째 생태계에 공유하는 절차는 기존 컨트롤러에서 커미셔닝 창을 열고 11자리 페어링 코드를 받아 새 컨트롤러에 입력하는 방식이며, Apple Home 은 기기 상세에서 "Turn On Pairing Mode", Google Home 은 "Set up without QR Code", SmartThings 는 "Share with other services", Google Home 설정에서는 "Linked Matter apps & services" 메뉴를 쓴다 — 원문: "Turn On Pairing Mode" / "Set up without QR Code" / "Share with other services" / "Linked Matter apps & services" [S3]
10. Home Assistant 도 같은 기기를 여러 컨트롤러에 붙이는 Multi Fabric 기능을 공식 안내하며, 다른 플랫폼 앱에서 QR 또는 공유 코드로 합류시킨다 — 원문: "One of the great features of Matter is the so-called Multi Fabric feature: you can join the same device to multiple controllers." / "To join the device to the other platform, in their app, scan the QR code or enter the sharing code." [S7]
11. Home Assistant 의 Matter 컨트롤러는 별도 프로세스인 Matter Server 앱(구 add-on)으로 돈다 — 원문: "The Home Assistant integration runs its own 'Matter controller' as an app (formerly known as add-on). This Matter Server app runs the controller software as a separate process." [S7]
12. matter.js 는 Apple iOS 17.1·Google·Amazon·SmartThings·Home Assistant 2024.5.2 등 생태계와의 페어링을 검증했고, Bridge 지원은 Apple·Google·Amazon·SmartThings·Home Assistant 에서 "X"(지원)로 표기된다 — 원문: "Apple iOS 17.1" / "Home Assistant 2024.5.2" / (Bridge 행) "X" [S4]

**(c) SDK · 개발킷**

13. nRF Connect SDK v3.2.0 의 Matter Light bulb 샘플은 Matter over Thread 보드 타깃으로 nRF5340 DK 와 nRF54LM20 DK 를 명시하고, Matter over Wi-Fi 는 nRF7002 쉴드를 붙인 nRF5340 DK·nRF54LM20 DK 로 지원한다 — 원문: "nrf5340dk/nrf5340/cpuapp" / "nrf54lm20dk/nrf54lm20a/cpuapp" / "nrf7002ek" / "nrf7002eb2" [S8]
14. 같은 샘플은 흰색 조광 전구 디바이스를 구현하며, 원격 제어에는 Matter over Thread 인 경우에만 Thread Border Router 구성이 필요하다 — 원문: "a white dimmable light bulb device" / "the Thread Border Router (only for Matter over Thread communication)" [S8]
15. matter.js 는 Matter 프로토콜 전체를 TypeScript 로 구현해 디바이스·브릿지·컨트롤러를 만들 수 있고, 예제 스크립트의 기본 VID/PID 는 0xFFF1/0x8000 이다 — 원문: "Please use 0xFFF1 as Vendor ID and 0x8000 as product id because matter.js uses this by the current example scripts by default." [S4]

**(d) Thread Border Router 필요 여부**

16. Home Assistant 공식 문서는 Thread 기반 Matter 기기를 추가하려면 기기 근처에 Thread border router 가 필요하다고 명시하며, iPhone 사용자에게는 HomePod Mini/V2·Apple TV 4K·HA OpenThread Border Router 앱, Android 사용자에게는 Nest Hub(2nd Gen)·Nest Wi-Fi Pro·HA OTBR 앱을 든다 — 원문: "To add a Matter device which is based on the Thread radio protocol, you need a Thread border router near the device" / "HomePod Mini or V2, Apple TV 4K or Home Assistant with the Home Assistant OpenThread Border Router app" / "Nest Hub (2nd Gen) or Nest Wi-Fi Pro or Home Assistant with the Home Assistant OpenThread Border Router app" [S7]
17. HA OTBR 용 동글로 Connect ZBT-1·ZBT-2·SkyConnect 가 언급된다 — 원문: "Connect ZBT-1, ZBT-2, or SkyConnect" [S7]

**(e) 미인증 기기 커미셔닝 제약**

18. Google 공식 문서상 VID 0xFFF1~0xFFF4 는 테스트용 예약값이고, 테스트 VID/PID 기기를 커미셔닝하려면 Developer Console 에 같은 VID/PID 조합의 integration 을 만들어 두어야 한다 — 원문: "VIDs `0xFFF1` — `0xFFF4` are reserved for testing." / "Make sure you have created an integration with the correct VID/PID combination in the Developer Console." [S6]
19. 인증된 양산 기기는 Google Home Console 프로젝트 없이도 커미셔닝된다(반대로 미인증 기기는 프로젝트가 필요하다는 뜻) — 원문: "For _production_ devices, the Google Home ecosystem supports commissioning and control of certified Connectivity Standards Alliance (Alliance) devices regardless of whether they have a project in the Google Home Console." [S6]
20. matter.js 공식 문서는 Apple·Google 에서 페어링 시 OS 가 'uncertified device' 허용을 묻고 이를 허용해야 하며, Alexa 는 별도 설정이 필요 없다고 적는다 — 원문: "When pairing with matter.js the operating system will ask you to allow to pair an 'uncertified device' which you need to allow." / "For Alexa no special setup is needed to pair with matter.js as development device." [S4]

**(f) Bridge(Aggregator) 사용**

21. Google Home 은 Matter 브릿지 뒤의 기기들이 일반 기기처럼 보인다고 명시한다 — 원문: "All devices behind a Matter bridge appear as normal for a user in the Google Home ecosystem." [S5]
22. matter.js 생태계 표에서 Bridge 는 Apple·Google·Amazon·SmartThings·Home Assistant 에서 지원("X")이고 LG ThinQ·Tuya 는 미지원("-")이다 — 원문: "X" / "-" (Bridge 행) [S4]

### 추론 (선택 — "추론:" 으로 시작)
- 추론: "Cluster 표준 준수" 점수를 위해서는 커스텀 클러스터 대신 **모든 컨트롤러가 이미 해석하는 표준 조합**으로 이벤트를 매핑하는 것이 안전하다 — 조류 감지 = Occupancy Sensor(Occupancy Sensing), 둥지 의심/장기 체류 = Contact Sensor(Boolean State) 엔드포인트 하나 더, 퇴치 액추에이터(서보·초음파·LED) = On/Off Light 또는 On/Off Plug-in Unit(On/Off, 필요 시 Level Control 로 강도). 이 세 타입은 Google 공식 지원 표에 스펙 1.0 부터 있고 [S5] Home Assistant 도 Binary sensor·Switch·Light 로 받는다 [S7]. Google 이 "표에 없는 타입은 공식 미지원"이라 못박으므로 [S5] manufacturer-specific 클러스터는 부가 진단 정보(예: 감지 종·신뢰도)에만 쓰고 채점 대상 동작에는 넣지 않는 것이 맞다.
- 추론: 1.5 카메라 디바이스 타입은 표준에 들어갔지만 [S1] nRF5340/nRF54LM20 급 MCU 로는 WebRTC 스트리밍을 감당하기 어렵고, 생태계 컨트롤러의 1.5 카메라 지원도 미확인이다. 카메라는 "온디바이스 AI 의 입력"으로만 두고 Matter 로는 **이벤트(Occupancy/Boolean)** 만 노출하는 설계가 현실적이다. 카메라 노드를 Matter 카메라로 굳이 노출하고 싶다면 ESP32-P4 기반 esp-matter 카메라(보조 확인)가 유일하게 문서화된 경로다.
- 추론: 하드웨어 분할 안 — (1) **nRF5340 DK 단일 노드**(Matter over Thread, 엔드포인트 3개: Occupancy·Contact·On/Off)에 라즈베리파이 AI 결과를 UART/BLE 로 넘겨 반영하는 안이 커미셔닝·상태 동기화 시연에 가장 단순하다. (2) 라즈베리파이에서 matter.js **Bridge(Aggregator)** 로 감지 이벤트를 노출하고 nRF5340 은 별도 Thread 액추에이터 노드로 두는 안은 노드 2개·fabric 관리 2배지만 Bridge 가 Apple·Google·SmartThings·HA 에서 지원됨이 문서화돼 있다 [S4][S5]. 예선 킷이 nRF 개발킷이므로 (1) 을 주축, (2) 를 확장으로 두는 것이 배점(Matter 30 + 상호운용 20)에 유리하다.
- 추론: Multi-Admin 시연 순서 — Apple Home 으로 1차 커미셔닝 → 기기 상세 "Turn On Pairing Mode" → Google Home "Set up without QR Code" 에 코드 입력 → SmartThings/Home Assistant 도 같은 코드 방식 [S3][S7]. 세 앱에서 Occupancy 상태가 동시에 바뀌는 화면이 "상태 동기화·복수 컨트롤러 연동" 채점 증거가 된다. Matter 1.4 의 Enhanced Multi-Admin·1.6 의 Joint Fabric(보조 확인)은 생태계 측 기능이라 해커톤 기기 구현 범위 밖이고, 기본 Multi-Admin(복수 fabric)만으로 충분하다.
- 추론: Thread 를 쓰면 Apple TV 4K/HomePod mini 또는 HA + ZBT-1/SkyConnect OTBR 이 시연장에 있어야 한다 [S7][S8]. 현장 네트워크가 불안정하면 nRF7002 쉴드로 Matter over Wi-Fi [S8] 또는 라즈베리파이 matter.js(이더넷/Wi-Fi) 로 전환하는 예비안을 준비한다. 다만 nRF7002 쉴드가 지급 킷에 포함되는지는 미확인.
- 추론: 미인증 기기 커미셔닝은 VID 0xFFF1 계열로 가능하되, Google Home 은 Developer Console 에 VID/PID integration 을 미리 만들어야 하고 [S6], Apple/Google 모두 'uncertified device' 허용 팝업이 뜬다 [S4]. 시연 전에 심사위원용 계정에서 이 등록·허용 절차를 리허설해 두어야 "Commissioning 성공률" 점수를 잃지 않는다.
